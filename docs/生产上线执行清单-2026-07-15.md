## 3. 目标 MySQL 环境验收

执行前必须由运维或 DBA 提供以下输入，不得把密码、证书私钥或完整连接串提交到仓库：

- [ ] 目标数据库稳定 DNS/代理端点、MySQL 版本和供应商信息。
- [ ] 只读检查账号、独立迁移账号、仅含模型表 DML 权限的运行账号。
- [ ] 供应商 CA；如使用双向 TLS，另提供客户端证书和受保护私钥。
- [ ] 数据库平台备份保留策略、加密策略、binlog/GTID 状态和 PITR 操作入口。
- [ ] 故障转移方案、允许的维护窗口、DDL 锁上限、RPO 与 RTO。

验收顺序：

1. 使用只读账号执行完整生产预检，任何 blocking 立即停止。
2. 把最新真实备份恢复到隔离实例，不覆盖唯一可用副本。
3. 在隔离实例执行 `fresh/history/retry`、schema upgrade、再次预检和核心业务冒烟。
4. 对比表数、逐表行数、主键摘要、库存、收费金额、处方状态和关键表全列校验和。
5. 验证 PITR、代理故障转移、应用 readiness 503 摘流及回退 RTO。

本机发现的旧 MySQL login-path 当前不能被客户端加载，校验停在认证前，未创建或修改 schema/账号。它不能替代目标环境凭据或验收结果。

数据处理约束：

- [ ] 原始 `ture.db` 设为只读并保留上述 SHA-256，所有操作只针对隔离副本。
- [ ] 修复前导出受控审计清单，记录表、主键、旧外键、批准人、理由和时间；清单按诊疗数据等级加密保存。
- [ ] 不删除业务行；如批准置空，在单个事务中按精确条件更新并核对影响行数必须等于批准数量。

- [ ] SQLite 到 MySQL 先执行 dry-run，再以源 SHA-256 和维护窗口停写证明执行正式导入。
