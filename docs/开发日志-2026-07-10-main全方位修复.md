# 开发日志：main 主线全方位修复（2026-07-10）

## 1. 本次目标与范围

- 修复基线：`main`，基线提交 `386d8e3`。
- 修复依据：现有功能、Git 历史、开发记录、二次开发分析和自动化测试。
- 处理原则：保持医生、护士、管理员、财务四角色及现有处方状态机兼容；不整体合并其他分支的实验能力。
- 默认数据位置统一为项目根目录 `data/app.db`；正式修改前已创建 SQLite 备份 `data/backups/pre-main-fix-20260710-202701.db`。

本轮属于主线稳定性和数据一致性修复，不对应新的发布标签。完整技术记录见
[《main 主线全方位修复记录》](主线全方位修复记录-2026-07-10.md)。

## 2. 配置、认证与安全

- 删除开发入口中的本机绝对数据库路径，源码、初始化脚本和打包入口统一默认使用 `data/app.db`。
- SQLite 作为零配置默认数据库；配置 `DATABASE_URL` 或 `SQLALCHEMY_DATABASE_URI` 后可连接外部 MySQL，生产入口不再覆盖外部配置。
- 未显式配置 `SECRET_KEY`、`JWT_SECRET_KEY` 时，在 `data/.runtime-secrets.json` 原子生成并持久化强随机密钥；Windows 使用全局命名互斥量，Linux 使用文件锁，避免多进程首次启动生成不同密钥。
- 基础账号改用 `BOOTSTRAP_PASSWORD` 或启动控制台输出的随机临时密码，不再提供公开固定密码；旧库仍使用公开默认密码的基础账号会在升级时自动旋转。
- GitHub Linux Release 的安装和发布说明同步移除固定初始密码，改为说明环境变量或启动日志中的随机临时密码。
- 创建账号、管理员重置和用户自助改密统一执行至少 12 位密码策略；`token_version` 使改密、重置或停用前签发的 JWT 立即失效。
- 管理员“删除账号”改为软停用，可重新启用，同时保留历史接诊、收费、盘点和操作日志的人员归属。
- 默认服务只监听 `127.0.0.1`；局域网监听需要显式配置，生产环境要求通过 HTTPS 反向代理提供服务。
- CORS 改为 `CORS_ORIGINS` 允许列表；请求体限制为 12 MB，Excel 导入增加解压体积、行数和列数上限。
- 未知 `/api/*` 返回 JSON 404；全局异常不再把内部异常文本返回客户端。
- 修复病例复盘打印中的存储型 XSS；财务接口和导出强制脱敏患者姓名，并移除学号、诊断、主诉等非财务必要字段。
- MySQL 初始化脚本移除共享明文密码，迁移工具从环境变量读取凭据；新增 `.env.example` 说明可配置项。

## 3. 数据库兼容与迁移安全

- 使用 `_sync_model_schema()` 以当前 ORM 模型为来源，幂等创建缺失表、可空字段和非唯一索引，兼容 SQLite/MySQL 历史数据库。
- 运行时同步只做增量补齐，不删除旧列；字段改型、非空/唯一/外键约束和复杂回填仍必须使用经过审查的 Alembic migration。
- 不再在 `main` 自动创建尚未实现的中医诊疗字段，避免模型与实际业务继续偏离。
- SQLite 连接统一启用外键约束和 15 秒写锁等待；患者类型历史回填改为事务提交。
- 患者拼音索引字段改为有界字符串；空值排序改用跨 SQLite/MySQL 的通用表达式。
- SQLite 到 MySQL 迁移使用单一源快照、目标模型表原子替换并在提交前校验外键孤儿；清理范围只包含 ORM 模型表，不删除扩展表、运维表或 `alembic_version`。
- 迁移专用配置关闭 APScheduler 和启动数据修复，避免迁移过程中后台任务并发写目标库；字符集转换也仅处理 ORM 模型表。
- 旧 MySQL 兼容升级补充 `user.password_hash` 长度，以及患者拼音字段从 `TEXT` 到 `VARCHAR(255)` 后再建索引的处理。

## 4. 库存流水、盘点与月报

- `InventoryRecord` 增加 `visit_id`，并新增 `dispense`、`reversal` 结构化操作类型。
- 处方执行时记录出库流水，撤销时记录返库流水；旧版已撤销交易在首次启动时幂等补记成对流水，首次撤销旧交易时也会补齐原出库记录。历史补记优先采用 `nurse_execute` 审计日志中的真实执行时间和经手人。
- 月报优先按结构化流水统计出库，跨日撤销分别落在执行日和撤销日，不再用当前库存反推而抹掉历史出库。
- 整装/零售库存组统一换算为最小基础单位并合并为一行，保持 `期初 + 入库 + 调整 - 出库 = 期末`。
- 历史期末读取截止日期次日北京时间零点快照；停用药品仍保留在历史报表中。
- 每日快照只由零点调度器在取得库存写锁后创建，白天重启不再生成错误期初；锁忙或临时数据库错误会持续重试，延迟生成的快照结合 `created_at` 和期间流水归一化到零点边界。
- 入库、盘点调整、智能合并均写结构化操作类型；保留对旧系统备注的兼容识别。
- 联合盘点统一使用库存组总量、整装换算量和零售份数，修复从零售变体打开时库存成倍放大的问题，并拒绝超出数据库整数范围的结果。
- CSV 导入按物资类型、批次和效期匹配，排除库存组，逐行保存点隔离并拒绝负数、NaN、Infinity。
- 智能盘库改为“扫描候选 -> 展示全部候选 -> 逐项勾选核对 -> 合并”；全部候选确认后才允许提交，执行时还会校验候选未变化，并迁移处方、流水、快照引用及写入操作审计。
- 护士入库补齐购进价，耗材追加或修改库存时同步采购成本。

## 5. 收费、营收与隐私

- 支付方式限制为现金、一卡通、其他；优惠标记必须为布尔值，金额必须有限、非负并按 `ROUND_HALF_UP` 归一为两位小数。
- 分项实收必须成对提交，不能与旧版实收总额混用，也不能超过对应应收金额。
- 职工优惠只允许用于 `patient_type=staff`，教职工处方默认勾选优惠。
- 新增统一收入分摊服务：总收入以 `Payment.amount` 实收为准，诊查、药品、诊疗项目、耗材四类按统一规则分摊，分位差额自动归集，分类之和严格等于总实收。
- 管理员统计、Excel 导出和财务看板统一收入口径，并移除财务占比查询中的 Visit N+1。
- 统计和导出按北京时间转换为 UTC 半开区间查询，修复凌晨收费归入错误日期的问题；医生和护士页面时间也固定按北京时间格式化。
- 财务患者姓名统一脱敏，包括单字姓名；月报 Excel 文本字段进行转义，阻止公式注入。
- 审核、驳回、改价、增删项目、执行和撤销使用相同 Visit/库存锁序，减少并发状态竞争。

## 6. 备份与恢复入口

- `GET /api/admin/backup` 根据当前数据库直接下载备份：SQLite 为 `.db`，MySQL 为 `.sql`。
- SQLite 使用在线 Backup API，避免直接复制正在写入的数据库或 WAL；临时下载文件在响应结束后清理。
- 保留 `POST /api/admin/backup` 作为旧版 SQLite 服务端备份兼容入口，最多保留 20 份。
- MySQL 使用 `mysqldump --single-transaction`，密码通过子进程环境传递而不出现在命令行，导出设置 300 秒超时并清理临时文件。
- MySQL 备份内部错误只写服务日志，不向客户端泄露命令或连接细节。

## 7. 前端工作流

- 医生、护士、财务端增加账号设置入口，复用改密组件；管理员账号管理继续支持重置和启停。
- Axios 统一处理登录失效的 401 和 JWT 相关 422，清理本地会话并跳回登录页；业务校验 422 不会被当成登录失效。
- 处方执行改用受控确认框，避免原生确认交互和异步流程不一致。
- 智能盘库展示全部合并候选，要求逐项勾选核对且全部完成后才能执行合并；候选变化时刷新并要求重新确认。
- 库存页面重新接回入库入口；管理端隐藏后端未支持的库存组操作，零售变体不再提交购进价。
- 月报导出统一通过 Axios 获取 Blob，并检查 HTTP 状态、鉴权失败、响应类型和空文件，错误响应不再被下载成伪 Excel 文件。
- 入库表单响应式栅格调整，账号设置页面兼顾桌面和移动端布局。

## 9. 尚未完成与后续验收

以下内容未在本轮完成，不能因 SQLite 本地回归通过而视为已验收：

1. 金额字段目前仍是 `Float`，尚未迁移为数据库 `Numeric/Decimal`；需要单独设计迁移、舍入规则和前后端兼容方案。
2. MySQL advisory lock、行锁、schema 同步/升级、SQLite 到 MySQL 真实迁移和 `mysqldump` 备份尚未连接真实 MySQL 做集成验收。
3. Git 历史中曾出现的旧 MySQL 凭据必须由部署方在所有环境轮换或删除；是否重写公开仓库历史仍需单独决策，不能只依赖当前文件已删除明文。
4. 前端尚未建立 Vitest 单元测试和 Playwright 端到端测试体系，目前前端验证仍以生产构建和人工流程审查为主。
5. 前端构建仍有约 991 KB 的 `request` 公共 chunk 告警，需要后续拆分 Element Plus 和公共依赖。
6. 预约叫号、中医诊疗、自动拆零 v3、配伍禁忌仍是其他分支的候选能力，本轮未合并进 `main`。
7. SQLite 多进程同时启动时，历史撤销流水回填尚无数据库级唯一约束；当前 `run_prod.py` 使用单进程 Waitress，不受此限制，多实例部署前仍需补充约束或跨进程互斥。
8. 登录接口尚无跨进程持久化限流；对公网部署时应先在 HTTPS 反向代理层配置登录限速，后续再引入共享存储限流方案。

## 10. 二次开发提示

- 新增或调整数据库字段时，不要把运行时结构同步当成完整 migration；涉及类型、约束、回填必须提交 Alembic 脚本并分别验证 SQLite/MySQL。
- 任何库存变化都应同时考虑数据库锁、`InventoryRecord` 结构化流水、历史月报和撤销路径。
- 金额统计必须通过统一收入分摊服务，不能在新接口中复制一套独立口径。
- 运行时密钥文件和数据库备份属于敏感数据，不得提交 Git 或随日志公开。
