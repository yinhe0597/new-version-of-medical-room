# 开发日志 open0.0.11（2026-05-27）

## 版本主题：护士端历史诊疗记录权限放开与多维筛选增强

### 功能背景

护士团队反馈：历史诊疗记录页面仅展示当前护士经手的记录，团队成员之间无法互相查看。当需要追溯其他护士处理过的处方时，需要切换账号或依赖线下沟通，影响协作效率。

此外，缺乏按护士、医生、日期的筛选能力，面对大量历史记录时定位困难。

---

## 一、权限修改 - 护士端历史记录全员可见

### 问题描述

`GET /nurse/my-history` 接口原本限制为仅返回当前登录护士经手的记录（通过 `verified_by`、`rejected_by`、`revoked_by`、`Payment.nurse_id` 四个关联字段筛选），其他护士处理的记录完全不可见。

### 影响

- 护士A无法查看护士B处理过的历史处方
- 值班交接时需要反复切换账号
- 管理层无法在一个账号下纵览全局

### 修复方案

移除 nurse_id 的硬编码限制（不再强制关联当前 `user_id`），改为**可选筛选参数**：
- 不传 `nurse_id` → 返回全部历史记录（所有护士可见）
- 传 `nurse_id` → 精确筛选该护士经手的记录

保持原有 "经手关联" 逻辑（verified_by / rejected_by / revoked_by / Payment.nurse_id）不变，仅从硬限制变为可选筛选项。

### 安全考量

撤销交易接口（`POST /nurse/visits/<id>/revoke`）保持原有的 "仅经手护士可撤销" 限制不变。查看权限放开 ≠ 操作权限放开，撤销交易涉及库存回滚和资金变动，仍需谨慎控制。

## 二、筛选功能增强 - 多维筛选

### 新增筛选维度

| 维度 | 前端控件 | 后端参数 | 说明 |
|------|---------|---------|------|
| 护士 | 下拉选择 | `nurse_id` | 选择特定护士，查看该护士经手的记录 |
| 医生 | 下拉选择 | `doctor_id` | 选择特定医生，查看该医生开立的处方 |
| 日期范围 | 日期区间选择 | `date_from` / `date_to` | 按就诊时间范围筛选 |

### 支持组合

- **任一护士 + 任一医生** → 精确匹配特定护士经手特定医生的记录
- **全体护士 + 任一医生** → 查看指定医生的所有记录（不限护士）
- **任一护士 + 全体医生** → 查看指定护士处理的所有医生记录

### 数据来源

新增 `GET /nurse/staff-list` 接口，返回所有医生和护士的 `{id, real_name}` 列表，支持角色分别下拉展示。

### 日期范围处理

`date_to` 包含当天全天（即 `date_to + 1天` 作为结束边界），符合"查询某日到某日"的直觉预期。

## 四、设计决策记录

### 为什么使用可选参数而非分角色权限？

三种方案对比：

| 方案 | 优点 | 缺点 |
|-----|------|------|
| A: 全员可见 + 可选筛选 ✅ | 实现简单，灵活度高 | 数据量大时需后端筛掉无关记录 |
| B: 保留原权限 + 管理员授权查看 | 粒度最细 | 增加了运维成本，不符合协作需求 |
| C: 新增独立查看角色 | 隔离清晰 | 过度设计，小团队无此必要 |

校内医务室护士团队规模小（通常 2-5 人），相互信任度高，选用方案 A 最简洁实用。

### 为什么查询按钮是显式的？

为避免每次下拉切换都触发 API 请求（导致不必要的网络开销），将护士/医生/日期筛选设置为"待提交"状态，用户点击"查询"按钮后统一请求。患者姓名搜索和状态筛选保持客户端即时过滤。
