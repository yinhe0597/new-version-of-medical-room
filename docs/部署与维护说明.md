# 校医务室诊疗管理系统部署与维护说明

更新时间：2026-07-13

## 1. 支持边界

- 源码部署要求 Python 3.10+，推荐使用与 CI 一致的 Python 3.11；Linux/Windows 打包制品不要求目标机安装 Python。
- 默认数据库为程序目录下的 `data/app.db`。
- 正式支持 MySQL Community Server 8.0.21+，驱动为 `mysql+pymysql`。
- MariaDB、PostgreSQL 和其他数据库未通过发布验收，不属于支持目标。
- 数据库在进程启动时选定。修改连接配置后必须完整重启，不支持运行中热切换、双写或自动回落。
- SQLite 到 MySQL 是维护窗口内的一次性全量迁移。MySQL 开放写入后，不得回切到冻结的 SQLite 文件。

## 2. 生产拓扑

- 应用默认监听 `127.0.0.1:5000`，由 Nginx、IIS 或云负载均衡通过 HTTPS 代理。
- `GET /api/health/live` 用于进程存活检查。
- `GET /api/health/ready` 对 MySQL 持续核对当前 database、读写状态、session strict mode、Alembic head 和运行账号授权；任一漂移或查询失败都会返回 503，此时应停止导入新流量。
- Linux tar 包的 `run.sh` 会把 HTTP 503 也视为端口已占用，禁止误启第二实例；PID 文件同时绑定进程启动时刻和随机令牌，身份无法证明时拒绝发送 TERM/KILL。`start`、`stop`、`restart` 和 `status` 通过 `flock` 串行执行；目标机必须提供 `flock`（通常由 `util-linux` 安装），缺失时脚本失败关闭。
- 多实例必须使用相同 `DATABASE_URL`、`SECRET_KEY` 和 `JWT_SECRET_KEY`。切库时必须停止全部实例和调度器。
- 推荐让应用始终连接一个稳定的 MySQL 代理或云数据库端点，由数据库层处理主备切换，不要在应用和 SQLite 之间做故障回落。

## 3. MySQL 准备

1. DBA 创建 `utf8mb4` 数据库。根目录 `init_database.sql` 只负责建库示例，不会安全创建生产账号。
2. 分离迁移账号和运行账号。迁移账号仅在维护窗口使用；运行账号只授予模型表的 `SELECT/INSERT/UPDATE/DELETE`。
3. 远程 MySQL 必须配置 CA 验证。将 `DATABASE_URL` 和证书路径注入服务 secret，不要写入仓库或命令行。
4. 生产机安装与服务端兼容的 `mysqldump`/`mysql` 客户端，或使用云数据库原生备份和 PITR。
5. `.env` 示例见根目录 `.env.example`。不得同时配置不同的 `DATABASE_URL` 和 `SQLALCHEMY_DATABASE_URI`，冲突会阻止启动。
6. MySQL URL 的 query 只允许 `charset`、`unix_socket` 和文档化的 `ssl_*` 项。`host/user/password/database/port/timeout/autocommit/init_command` 及未知项会在任何连接前阻断；允许项会转入直接 PyMySQL 参数，engine 初始化前的应用配置不保留任何用户 query。Flask-SQLAlchemy 可能在 engine URL 上补回固定的 `charset=utf8mb4`，但不会保留用户可控的目标或 TLS 项。自定义配置中的 `connect_args` 同样不能覆盖连接目标，声明 socket 必须与实际 socket 完全一致。

## 4. 只读生产预检

源码部署：

```powershell
& backend\.venv\Scripts\python.exe scripts\check_production_database.py
& backend\.venv\Scripts\python.exe scripts\check_production_database.py --json
```

打包部署：

```powershell
.\医务室管理系统.exe --check-database
.\医务室管理系统.exe --check-database --json
```

预检只执行 `SELECT`、`SHOW` 或只读 SQLite PRAGMA，并为 MySQL 连接、读写和深度查询设置超时。显式 `--check-database` 默认执行完整检查；生产启动默认使用有界 profile，跳过可能昂贵的外键全表扫描，并提示在发布门禁中单独执行完整检查。

检查范围：

- 连接目标与密码脱敏、支持的驱动和唯一 Alembic head。
- MySQL 版本、TLS、utf8mb4、严格模式、InnoDB、读写状态和时区。
- 运行账号最小 DML 权限、模型表/列/索引/唯一约束/外键差异。运行账号的 `*.*` 除 `USAGE` 外一律阻断；角色授权或无法解析的授权按失败关闭处理。
- 所有模型外键的悬空记录。

任一 blocking 项都必须阻止发布。临时网络/超时故障会进入有限启动重试，配置、权限、schema 等永久错误立即退出。远程 MySQL 未提供 CA 验证或 URL 包含 `ssl_disabled=true` 时，工具不会先尝试连接。

## 5. Schema 升级

迁移链是 forward-only，不支持离线 `--sql` 或跨当前边界 downgrade。升级前必须停止全部应用实例并验证备份。

源码部署也应走受保护入口（不要在生产直接绕过备份门禁调用 Flask-Migrate）：

```powershell
& backend\.venv\Scripts\python.exe run_prod.py --migrate-database `
  --backup-file D:\backup\medical_db_backup_20260713_120000.zip --yes
```

打包部署使用同一个后台下载的 MySQL ZIP：

```powershell
.\医务室管理系统.exe --migrate-database `
  --backup-file D:\backup\medical_db_backup_20260713_120000.zip --yes
```

ZIP 内必须且只能包含一个 SQL 和它的 `.sql.manifest.json`。命令会安全读取内部条目、流式重算 SQL 大小和 SHA-256，并核对清单绑定的 MySQL host、port、database、`server_uuid`、Alembic head 及可用时的 GTID 状态；任一不匹配都会在 DDL 前阻断。备份默认只能在生成后 60 分钟内用于迁移，可通过 `MIGRATION_BACKUP_MAX_AGE_MINUTES` 在 1 到 1440 分钟内收紧或调整。外部工具生成的 SQL 仍可与相邻同名 v2 manifest 一起使用。所有 MySQL 的生产启动都强制关闭运行时 schema 同步、开启预检并要求唯一 Alembic head，不能通过环境变量关闭。

下载备份前先停止全部应用写入，并保持停写直到迁移及 postflight 完成。备份过程会比较 dump 前后的实例、版本和 GTID 状态；启用 GTID 时，迁移前还会拒绝备份后发生过写入的目标。只有 `@@GLOBAL.gtid_executed` 查询成功且返回空值时，才按“GTID 未启用”记录并要求人工证明持续停写；查询报错、超时或权限不足都会直接阻断备份和迁移，不会降级放行。

## 6. SQLite 到 MySQL 数据迁移

先升级 MySQL schema，再运行 dry-run。不要运行 `backend/init_db.py`，该脚本包含开发初始化数据。

源码 dry-run：

```powershell
& backend\.venv\Scripts\python.exe backend\migrate_to_mysql.py `
  --source data\app.db
```

打包 dry-run：

```powershell
.\医务室管理系统.exe --import-sqlite data\app.db
```

dry-run 会创建 SQLite 在线快照，执行 `quick_check`，检查目标 Alembic head、表列完整性、全部实际外键孤儿、逐表行数和主键摘要，并打印源快照 SHA-256。它不会修改目标。

停止所有源库写入后，使用 dry-run 输出的摘要执行：

```powershell
.\医务室管理系统.exe --import-sqlite data\app.db `
  --execute --yes `
  --expected-source-sha256 <dry-run输出值>
```

源文件在 dry-run 后发生任何变化都会导致执行被拒绝。目标必须使用 strict SQL mode、可写 session 且所有模型表均为 InnoDB；这些事务前提会在 dry-run 和清表前各检查一次。目标模型表会在单个 MySQL 数据事务内全量替换，复制完成后再次核对行数、主键和数据库中全部实际外键，再提交。

以下情况会明确阻断，不能通过跳过字段继续发布：

- 源库存在外键悬空记录。
- MySQL 中存在模型表与非模型扩展表之间的任意方向外键；扩展表不会被清理或写入，存在交叉引用时无法安全执行全量替换。
- 源/目标缺少当前模型字段。
- 源库含目标不能保留的历史扩展字段，或目标含源无法填充的扩展字段。
- 目标不是当前唯一 Alembic head，或 dry-run 后目标数据发生变化。
- 目标 session 非 strict/只读/自动提交，或任一模型表不是 InnoDB。

## 7. 备份与恢复演练

- 后台 MySQL 备份使用 `mysqldump --single-transaction --quick --hex-blob`，支持 TCP/TLS 与 Unix socket。服务端把 SQL 与含生成时间、实例 UUID、Alembic head 和 GTID 标记的 manifest 原子封装为一个 ZIP；浏览器重算实际接收 ZIP 的 SHA-256 后才保存，避免 sidecar 被浏览器多文件策略拦截。
- 应另外启用数据库侧定时备份、保留策略、加密和 PITR。应用下载不能替代数据库平台备份。
- 每个发布候选必须把真实 dump 恢复到隔离数据库，核对 SHA-256、表数、逐表行数、主键、库存、收费金额和处方状态。
- 在恢复库上执行 `预检 -> upgrade -> 预检 -> 核心业务冒烟`，确认可恢复后才能进入生产维护窗口。
- 项目不提供生产库一键恢复接口。恢复必须写入新库/新实例，验证后再切换连接，避免覆盖唯一可用副本。

## 8. 切换与回退

1. 停止全部应用实例，记录发布 SHA、数据库目标和维护开始时间。
2. 创建最终 SQLite/MySQL 备份并核对 SHA-256 或 PITR 时间点。
3. 完成 schema 升级、数据迁移和只读预检。
4. 使用运行账号注入唯一 `DATABASE_URL`，完整重启应用。
5. 确认 readiness 为 200，再依次验证登录、查询、开方、审核、执行、撤销、入库、报表和备份。
6. 恢复流量后持续监控数据库连接、503、慢查询、锁等待、磁盘和复制延迟。

失败时禁止执行 downgrade。应从已验证备份/PITR 恢复到新库，运行预检后切换稳定数据库端点。MySQL 已接受写入后，回切旧 SQLite 会造成确定性数据丢失。

## 9. 发布门禁

- 后端全量测试、迁移/生产预检定向测试、Python compileall、`npm ci && npm run build` 全部通过。
- 最终 EXE/AppImage 必须实际执行 `--help` 和 `--check-database`；打包迁移还要用真实 dump+manifest 在隔离 MySQL 上执行 DDL。AppImage smoke 必须从只读镜像目录读取外部 `.env`，并把 `data/logs` 写到镜像旁可写目录或 XDG data 目录。
- CI 和目标环境都必须在授权隔离 MySQL 上完成 `fresh/history/retry` Alembic 验收；CI 结果不能替代目标云供应商环境复验。
- 在目标供应商环境单独验证 TLS、代理/故障转移、PITR、GTID/binlog、DDL 锁时长和恢复 RTO。
- 多实例发布前仍需完成数据库级业务幂等约束和并发压力测试。
- 服务管理器必须以非零退出码作为启动失败；生产入口缺少 Waitress、数据库永久阻断或自动重试耗尽时均会返回失败，不应配置为“退出 0 才重启”。
