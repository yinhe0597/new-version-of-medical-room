# 本地开发与部署常见问题记录

本文记录一次本地联调过程中遇到的关键问题、根因与规避方式，用于避免在实际部署/交付环境中重复踩坑。

## 1. 前端无法启动（npm/vite 找不到）

**现象**
- `npm`/`node` 无法识别
- `vite is not recognized ...`

**根因**
- 机器未安装 Node.js（或 PATH 未配置）

**规避/解决**
- 部署/开发机必须安装 Node.js（建议 LTS），并确保 `node`/`npm` 在 PATH 中可用
- 若使用便携 Node（如 `E:\yws2\node-v22.12.0-win-x64`），启动前显式加 PATH：
  - `$env:PATH="E:\yws2\node-v22.12.0-win-x64;"+$env:PATH`

**验证**
- `http://localhost:5888/` 可访问（前端 Vite 默认端口为 5888）

## 2. 登录接口报错 `net::ERR_CONNECTION_REFUSED http://localhost:5888/api/auth/login`

**现象**
- 登录失败
- 浏览器网络报 `ERR_CONNECTION_REFUSED` 指向 `http://localhost:5888/api/auth/login`

**根因**
- 本质不是“账号密码错误”，而是服务未启动：
  - 5888 前端未运行时：连 `localhost:5888` 都会被拒绝
  - 5888 正常但 5000 后端未运行时：前端代理 `/api` 会报 `ECONNREFUSED 127.0.0.1:5000`

**规避/解决**
- 确保两端都在跑：
  - 前端：`http://localhost:5888/`
  - 后端：`http://127.0.0.1:5000/`
- 前端代理配置在 [vite.config.js](file:///e:/yws2/medical-room-management-system/frontend/vite.config.js)：
  - `/api` → `http://127.0.0.1:5000`

## 3. 后端无法启动（系统 python 不存在）

**现象**
- `python` 无法识别

**根因**
- 机器未安装 Python（或 PATH 未配置）

**规避/解决**
- 部署/开发机安装 Python 3.10+（推荐 3.11/3.12），并确保 `python` 在 PATH 中
- 如临时使用嵌入式 Python（python-embed）：
  - 需额外处理 `pip`/`site-packages`（嵌入式包默认不包含 `ensurepip`、`venv`）
  - 推荐生产/部署环境使用标准 Python 安装包或容器镜像，避免嵌入式 Python 的维护成本

## 4. 后端启动报错：`View function mapping is overwriting an existing endpoint function: api.backup_database`

**现象**
- Flask 启动时直接 AssertionError，提示 endpoint 被重复覆盖

**根因**
- 在同一个 Blueprint 下，存在两个同名 view function：`backup_database`
- 且都绑定到同一路径 `/admin/backup`（GET 与 POST），导致 endpoint 冲突

**规避/解决**
- 已修复为不同函数名，并提供统一下载入口：
  - SQLite/MySQL 下载：`GET /api/admin/backup`（分别返回 `.db` / `.sql`）
  - MySQL 兼容入口：`GET /api/admin/backup/mysql`
  - 旧版 SQLite 服务端备份兼容：`POST /api/admin/backup`
- 对应实现文件： [admin.py](file:///e:/yws2/medical-room-management-system/backend/app/api/admin.py)

## 5. 登录一直失败（401/Bad username or password）

**现象**
- 后端返回 401：`{"msg":"Bad username or password"}`
- 或前端跳回 `/login`

**根因**
- 数据库未初始化，默认账号不存在

**规避/解决**
- 首次部署/首次本地启动必须执行初始化脚本创建默认账号与示例数据：
  - 运行 [backend/init_db.py](file:///e:/yws2/medical-room-management-system/backend/init_db.py)
- 基础账号为 `admin`、`doctor`、`nurse`，初始密码取 `BOOTSTRAP_PASSWORD`；未配置时由初始化脚本生成并打印随机临时密码。
- 系统不再提供公开固定密码。需要紧急重置时，先设置至少 12 位的 `RESET_PASSWORD`，再运行 `backend/reset_default_passwords.py`。

## 6. 前端路由相关警告（Vue Router 5）

**现象**
- 控制台出现：
  - “named route has a child without a name, an empty path...”
  - “next() is deprecated...”

**规避/解决**
- 路由守卫使用 return 值，而不是 `next()`
- 默认重定向建议使用父路由级 `redirect`，避免 “空 path 子路由” 在命名路由下触发警告
- 文件位置： [router/index.js](file:///e:/yws2/medical-room-management-system/frontend/src/router/index.js)

## 7. 部署前检查清单（建议）

- **端口**
  - 5888（前端）可访问
  - 5000（后端）可访问
- **配置**
  - `SECRET_KEY`、`JWT_SECRET_KEY` 生产环境必须通过环境变量配置，不使用默认值
  - 数据库连接串 `SQLALCHEMY_DATABASE_URI` 正确（sqlite 或 mysql）
- **初始化**
  - 首次部署执行 `init_db.py` 或等价初始化逻辑，确保账号/基础数据存在
- **外部依赖**
  - 若使用 MySQL 备份下载接口（`/api/admin/backup/mysql`），生产机需具备 `mysqldump`

## 8. 管理端“导入模板”下载后内容为空

**现象**
- 点击“下载导入模板”，下载到的文件是空内容

**根因**
- 前端下载 blob 的处理方式不正确，创建 Blob 时取了不存在的 `res.data`，导致实际写入为空

**规避/解决**
- 已修复为直接使用后端返回的 blob 生成下载文件
- 相关页面：[PatientManagement.vue](file:///e:/yws2/medical-room-management-system/frontend/src/views/admin/PatientManagement.vue)

## 9. 护士端“去审核”进入详情页报错（获取处方详情失败/500）

**现象**
- 护士端待处置列表点击“去审核”，提示“获取处方详情失败”

**根因**
- 后端对 `Visit.items` 使用了 eager loading，但模型关系为 `lazy='dynamic'`，会触发 SQLAlchemy 异常并返回 500

**规避/解决**
- 已修复为：只 preload `patient/doctor`，处方明细通过 `visit.items.options(...).all()` 拉取
- 对应接口：`GET /api/nurse/visits/<visit_id>`
- 同时前端会展示后端错误 `msg`（便于排查）

## 10. 开方时间在医生端/护士端显示不一致

**现象**
- 护士端审核页面显示的“开方时间”与医生端不一致（常见差 8 小时）

**根因**
- 数据库存储为 UTC（`datetime.utcnow`），接口直接 `strftime` 输出导致时区未转换

**规避/解决**
- 已修复为：接口输出时将 UTC 转为本地时区后再格式化
- 涉及接口：
  - `GET /api/doctor/visits/history`、`GET /api/doctor/visits/<id>`
  - `GET /api/nurse/pending-visits`、`GET /api/nurse/visits/<id>`

## 11. 编译打包遗漏代码变更（EXE 版本滞后）

**现象**

- 在 dev 模式下（`python run.py` + `npm run dev`）修改的功能正常工作
- 但编译打包后的 EXE 中部分修改未生效（如财务端仍能看到已移除的菜单项）

**根因**

- 开发者修改代码后只执行了 `vite build`（前端构建），**未执行 `pyinstaller` 重新打包**
- 用户拿到的是上一次打包的旧 EXE，前端 dist 文件和后端 Python 字节码均未更新

**典型触发场景**

1. 在 dev 环境下修改并验证通过
2. 执行 `git commit` 保存代码
3. 以为代码已保存 = 编译产物已更新，跳过 pyinstaller 步骤
4. 直接将旧 EXE 交付测试/部署

**规避/解决**

编译部署的完整链条必须全部执行，不可跳过中间步骤：

```bash
# === 完整编译部署流程 ===

# 1. 构建前端（必须）
cd frontend
npx vite build

# 2. 打包 EXE（必须——只有在第一步成功之后才能确保产物最新）
cd ..
pyinstaller medical_room.spec

# 3. 复制产物到部署目录
Copy-Item "dist\医务室管理系统.exe" "D:\yiwushi\yws20260603\" -Force
```

**检查清单**

| 检查项 | 说明 |
|--------|------|
| ✅ `vite build` 成功 | 确认所有前端模块编译无报错 |
| ✅ `pyinstaller` 成功 | 确认 EXE 重新生成，检查 dist 目录文件的修改时间 |
| ✅ 产物复制到目标目录 | 确认目标目录 EXE 的修改时间为本次打包时间 |

**经验教训**

- `git commit` 只保存了源码，**不等于**编译产物已更新
- 检查 EXE 修改时间是否晚于最后一次代码变更时间，是最直接的验证手段
- 前端修改 + vite build + pyinstaller 三步缺一不可，任一步骤遗漏都会导致交付物与源码不一致
