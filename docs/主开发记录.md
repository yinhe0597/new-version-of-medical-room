## 主干不污染约定（建议固定执行）

- 主干（main/master）只接收经过验证的合并，不在主干上做试错性提交。
- 每个需求/版本使用独立分支开发（例如 `feature/v1.06-*`），打包也在该分支或对应 tag 的干净工作区完成。
- 构建产物统一输出到约定目录（例如 `artifacts/` 或 `release/`），并通过 `.gitignore` 永久忽略，避免主干/分支被打包文件污染。
- 每次打包必须落一条“编译记录”：包含时间、目标版本、构建命令/环境、产物清单、问题与解决方式、以及打包前的代码变更快照（文件列表或 diff 统计）。
- 每个可交付版本建议用 tag 固化（例如 `v1.06`），并在 [README.md](file:///e:/yws/README.md) 的“更新日志”中维护对应条目。

## 版本调度（如何随时调动）

- 定位版本：先在“版本索引”表里查到对应的 tag/commit/分支。
- 切换代码：切到对应 tag/commit/分支后再进行调试或二次打包，避免用“半成品工作区”生成不可复现的产物。
- 定位产物：按“版本索引”的产物路径找到对应交付包（产物建议放到仓库外或被忽略目录）。
- 定位构建细节：按日期进入 `docs/编译记录/`，找到对应打包日的记录，复现命令与环境。

## 目录建议（便于长期维护）

- `docs/主开发记录.md`：主入口（版本索引 + 规范）
- `docs/编译记录/YYYY-MM-DD.md`：每日编译/打包流水
- `artifacts/<版本>/...` 或仓库外固定目录：交付包与校验信息（不入库）
