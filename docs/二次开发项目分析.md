## 1. 结论先行

这是一个已经能覆盖学校医务室日常核心业务的单体 Web 系统，主线闭环为：

`患者建档/检索 -> 医生接诊开方 -> 护士审核 -> 抓药/项目调整 -> 收费并扣减库存 -> 小票 -> 报表/审计`

当前 `main` 适合作为二次开发基线，但不适合立即叠加大功能。建议先完成配置、数据库迁移、库存一致性、财务口径和测试基线治理，再开发预约、中医、配伍禁忌等新模块。

需要特别区分三类内容：

1. `main` 已实现并实际可调用的功能：四角色工作台、西医接诊、处方审核、库存、收费、报表等。
2. 只存在于其他分支的候选功能：预约大厅/叫号/中医诊疗在 `origin/dev`，自动拆零重构/药品配伍禁忌在 `origin/new_data`。
3. 文档或兼容代码中出现、但 `main` 未真正实现的功能：例如中医字段的 SQLite 补列代码仍在主线，但主线模型、API、页面不含完整中医功能。

## 3. 技术架构与运行链路

### 3.1 主运行栈

- 前端：Vue 3、Vite 8、Element Plus、Pinia、Vue Router 5、Axios
- 后端：Python Flask、Flask-SQLAlchemy、Flask-Migrate、JWT、CORS
- 数据库：当前生产入口以 SQLite 为主；配置层声明可切换 MySQL
- 生产服务：Waitress，4 线程；失败时回退 Flask 开发服务器
- 打包：PyInstaller，提供 Windows、Linux tar.gz、AppImage 脚本
- 定时任务：
  - `run_prod.py` 每日库存快照线程
  - Flask-APScheduler 每 30 分钟清理过期挂单

### 3.2 前后端边界

- 所有业务 API 挂载在 `/api`
- Axios 统一注入 `Authorization: Bearer <token>`
- Vite 开发端口 `5888`，代理 `/api` 到 `127.0.0.1:5000`
- 生产时 Flask 同时托管构建后的 Vue 静态资源和 SPA 路由回退
- 当前源码共 80 条 Flask 路由，其中包含 4 条示例/调试路由
- 前端 `src/views` 下 26 个业务页面，共 29 个 Vue 组件

### 3.3 三个后端入口的实际差异

1. `backend/run.py`：开发服务器，但硬编码数据库到 `D:\yiwushi\open0.0\data\app.db`。
2. `backend/init_db.py`：按 `Config` 读取数据库；未设置变量时，默认位置取决于当前工作目录。
3. `run_prod.py`：正式入口，强制使用项目/EXE 旁的 `data/app.db`，创建 `data/logs/backups`，启动 Waitress、快照线程和崩溃重启。

因此 README 中“直接运行 `python run.py` 得到项目内默认 SQLite”的说法与代码不一致。二次开发应先统一入口和数据库位置，避免开发、测试、打包各连一份数据。

### 3.4 Java 目录定位

`backend-java/` 不是运行时微服务，也未被 Flask、前端或打包脚本调用。它只是 v1.10 时用于验证药品规格解析、最小价格和整散记录生成的 Java 17/Maven 实验模块。实际业务使用的是 `backend/app/services/drug_stock.py`。

## 4. 当前主线功能地图

### 4.1 公共能力

- 用户名/密码登录，JWT 7 天有效
- 后端按角色校验，前端按角色做路由守卫
- 当前登录用户修改密码
- 网络中断提示及 5 秒健康探测恢复
- 操作日志、病历修改留痕、小票数据快照

正式角色为 `doctor`、`nurse`、`admin`、`finance`。初始化脚本只自动创建管理员、医生、护士；财务账号需管理员创建。

菜单和能力：

- 患者接诊

- 完整/快速接诊
  - 主诉、现病史、既往史、体格检查、诊断、医嘱、特殊备注

  - 默认诊查费 8 元
  - 药品、诊疗项目、耗材统一选取
  - 普通用药、零散用药、静脉配伍分组

## 5. 核心数据与业务规则

### 5.1 核心实体

- `User`：账号和角色
- `Patient`：四类患者及学生/身份证/单位字段
- `Drug`：药品、诊疗项目、耗材共用字典和库存记录
- `DrugStockGroup`：同批次整装/零售变体共享的最小单位库存
- `Visit`：病历、金额和处方状态
- `PrescriptionItem`：处方条目、价格快照、成本、改价审计、静脉配伍
- `Payment`：实收、支付方式、优惠分项和小票快照
- `InventoryRecord`：手工调整和入库流水
- `DailyStockSnapshot`：月度报表期初/期末辅助数据
- `DiagnosisDict`：ICD-10 和医生自定义诊断沉淀
- `TextTemplate`：医生个人文本模板
- `ParkedVisit`：挂单草稿
- `OperationLog`：关键操作审计及部分病历修改详情

### 5.2 处方状态机

```text
pending ---------> nurse_verified ---------> completed ---------> revoked
   |                     |
   +---------------------+------------------> rejected
```

- `rejected` 和 `revoked` 都是旧 Visit 的终态。
- “重新开方”不是把旧记录退回 pending，而是载入旧内容后创建新 Visit。
- 护士未审核不能直接执行；自动化测试覆盖了这条约束。

### 5.3 三类物资

- `type=1`：药品，计收入、成本和库存，可普通/散装/库存组销售
- `type=2`：诊疗项目，计服务收入，通常不扣库存
- `type=3`：耗材，计耗材收入、成本和库存

### 5.4 两套库存机制并存

旧机制：一个 Drug 记录保存整装库存，`has_scattered + conversion_rate` 在散装执行时折算并按整包装向上扣减。

新一些的库存组机制：护士入库创建整装和零售两个 Drug 变体，共享 `DrugStockGroup.total_units`；开方和执行按 `quantity * unit_amount` 扣最小单位，再反算两个变体可售数量。

处方提交只检查库存，不预占；实际扣减发生在护士执行。撤销时按相同规则返还。

## 8. 二次开发前必须处理的风险

### P0：先处理，否则新功能会放大风险

1. **数据库入口不一致**
   `run.py`、`init_db.py`、测试和 `run_prod.py` 可能指向不同 SQLite 文件。应只保留环境变量/统一本地配置，不再硬编码 D 盘。

2. **数据库迁移体系不完整**
   SQLite 依赖 `_ensure_sqlite_column()` 临时补列；MySQL 老库只能依赖 Alembic，但当前迁移未覆盖患者类型、有效期、存放位置、优惠分项等大量后期字段。`db.create_all()` 只能创建新表，不能升级既有 MySQL 表。

3. **主线存在中医“幽灵字段”**
   `create_app()` 会向 SQLite 添加 23 个中医相关列，但主线 ORM 模型并未定义这些字段，API/页面也无中医功能。这些补列来自 dev 线，不应继续被描述成 main 已上线功能。

4. **库存有并发超卖窗口**
   开方、审核和执行均先读库存再写，核心库存查询没有行锁或乐观版本号。Waitress 4 线程或 MySQL 多实例下，两笔处方可能同时通过校验。Payment 唯一约束只能防重复支付，不能防不同 Visit 争抢同一库存。

5. **智能盘库具有破坏性合并风险**
   接口会按“名称+规格”自动合并并删除重复 Drug，没有把批次、有效期、库存组作为隔离条件。不同批次/效期可能被错误合并，且会影响处方引用和库存组关系。建议拆成“只扫描生成建议”和“管理员确认合并”两步。

6. **系统设置的备份按钮与后端不匹配**
   前端调用 `GET /admin/backup` 并期待下载 `.sql`；后端 SQLite 备份是 `POST /admin/backup` 且只返回 JSON，MySQL 下载则是 `GET /admin/backup/mysql`。当前按钮会得到 405，备份功能不能按界面说明工作。

7. **生产安全默认值不可直接使用**
   自动创建 `admin/doctor/nurse` 且密码均为 `123456`；SECRET/JWT 有弱默认值；`CORS(app)` 全开放；生产全局异常响应还返回异常文本。上线前必须强制首次改密、使用强环境密钥、限制来源和隐藏内部错误。

### P1：在业务扩展前定版

1. **优惠收入分类不守恒**
   Payment 总营收使用实收金额，但按类型统计仍使用 Visit 原诊查费和处方原/改后应收金额。发生职工优惠时，“分类收入合计”会大于实际 Payment 营收；新增的两个实收字段尚未进入统计口径。

2. **后端收费参数缺少边界校验**
   后端可接受任意 `payment_method`，优惠实收金额直接 `float()`，没有非负、上限、有限数和两项同时存在的严格校验。前端 `min=0` 不能代替服务端规则。

3. **金额统一使用 Float**
   多处依赖 `round(..., 2)`，财务长期累计存在二进制浮点误差风险。建议数据库改 Decimal/Numeric，后端统一金额工具，迁移和报表一起回归。

4. **库存流水语义偏弱**
   `InventoryRecord` 只有 old/new/remark，没有业务类型、批次、关联单据、最小单位变化量。月报需要从多张表和备注推断，后续加入采购、退库、报损时会越来越难对账。

5. **API 文档严重滞后**
   `docs/接口清单.md` 标注“全量”，实际只覆盖约一半接口，遗漏审核/驳回/撤销、挂单、月报、患者管理、财务等功能，且部分权限说明已经过期。

6. **前端没有自动化测试**
   当前没有 Vitest/组件测试/E2E 测试。打印、驳回重开、折扣、路由权限等历史上多次回归，建议至少增加 Playwright 核心流程测试。

### P2：技术债治理

- 约 80 个路由集中在几个大文件中，`admin.py` 和 `nurse.py` 已超过 2,000/1,900 行，应按患者、库存、收费、报表拆服务层。
- 仍保留 `/api/protected`、`/api/admin-only`、`/api/doctor-only` 示例接口，生产可移除。
- 启动时静默吞掉多处迁移/调度异常，会造成“服务启动成功但部分能力失效”。
- 时间处理混用 UTC 存储、`datetime.now()` 和手工 `+8小时`，应统一为带时区时间。
- README、WIKI、部署文档在 SQLite/MySQL、Vue Router 版本、默认路径上互相矛盾。
- `migrate_to_mysql.py` 默认 root/123456，`init_database.sql` 内置共享 MySQL 密码，不符合生产凭据管理要求。

## 9. 建议的二次开发顺序

### 阶段 A：建立可信基线

1. 从 `main@386d8e3` 创建新的二次开发基线分支。
2. 固定 Python、Node、npm 版本和锁文件，清理虚拟环境跟踪规则。
3. 统一开发/测试/生产配置和数据库位置，提供 `.env.example`，禁止代码内生产凭据。
4. 明确生产继续用 SQLite 还是迁移 MySQL/PostgreSQL；不要同时把两者都当主要路径。
5. 生成一条从当前完整模型到目标数据库的可重复迁移基线，并拿生产库副本演练升级/回滚。
6. 修复备份并做“备份后实际恢复”验收。

### 阶段 B：守住库存和金额

1. 定版普通药品用药字段规则，修复失败测试。
2. 统一旧散装和库存组机制，至少明确新增数据只能走哪一套。
3. 为审核、执行、撤销增加数据库级并发控制和幂等测试。
4. 将智能盘库自动合并改为可审计、可预览、可确认的流程。
5. 统一实收、应收、优惠、成本和分类报表口径。
6. 补齐负金额、非法支付方式、重复执行、重复撤销、库存组缺失等测试。

### 阶段 C：补产品级质量

1. 更新 API 文档或引入 OpenAPI 自动生成。
2. 增加 Playwright：登录、完整接诊、审核、收费、撤销、报表、权限越权。
3. 对患者身份证、手机号、病历、财务报表制定数据权限、备份保留和日志脱敏策略。
4. 增加数据库备份、恢复、迁移、库存/财务对账的发布检查清单。

### 阶段 D：选择业务扩展

推荐按价值和耦合度选择，不建议同时展开：

1. **预约/叫号**：从 `origin/dev` 提取 Appointment、在线医生、排队状态机；先做 API 和权限，再做大屏。
2. **数据分析看板**：可复用 dev 的指标设计，但必须先修正优惠/收入分类口径。
3. **药品配伍禁忌**：从 `origin/new_data` 提取规则模型和强制确认审计，适合在现有西药流程上独立落地。
4. **自动拆零重构**：价值高但数据迁移风险最大，应单独立项并使用真实药品数据演练。
5. **中医诊疗**：模型和页面较多，涉及中药计价、库存、处方打印、报损审批，建议作为独立子域，不直接塞进现有 VisitForm 大组件。

## 10. 开工前需要业务方确认的问题

1. 生产数据库以 SQLite 还是 MySQL 为准？是否已有真实数据库需要无损升级？
2. 普通药品的用法、用量、频次、时间是四项必填、至少一项，还是按剂型配置？
3. 职工优惠允许低于成本、0 元或高于应收吗？报表按实收如何拆分药品/诊疗/耗材？
4. 库存是否需要按批次和有效期独立核算，是否采用先进先出？
5. “智能盘库”是否真的允许自动合并不同批次，还是只应生成异常清单？
6. 撤销交易是否需要管理员审批、时间窗口或班次结账限制？
7. 医生是否应查看全校所有历史病历，护士是否应查看全部收费记录？
8. 下一阶段优先目标是预约叫号、配伍禁忌、自动拆零、中医诊疗，还是先做数据/安全治理？
